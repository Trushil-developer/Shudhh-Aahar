# Architecture Overview

Shuddh Aahar is a React Native (bare, 0.76) app for iOS and Android that scans UK supermarket
products (barcode or photo) and returns a personalised health verdict, generated by Claude
(Anthropic) and cross-referenced against the user's own health profile, NHS-informed rules,
and live UK price comparison data.

|---|---|
| Framework | React Native 0.76 (bare workflow, not Expo) |
| Language | TypeScript |
| Navigation | React Navigation v6 (native-stack + bottom-tabs) |
| Auth | AWS Cognito (+ Google Sign-In as federated IdP) |
| Backend API | AWS AppSync (GraphQL), JS resolvers, no Lambda |
| Database | AWS DynamoDB |
| AI | Anthropic Claude (Haiku 4.5 for verdicts/recommendations, Sonnet 4.6 for document extraction) |
| Product data | Open Food Facts API |
| Price comparison | Trolley.co.uk (HTML scraping, no official API) |
| Payments | Stripe (web checkout) + Apple IAP + Google Play Billing |
| Health data | Apple HealthKit (iOS) / Health Connect (Android) |
| Infra as code | Terraform (`terraform/`) |
| CI/CD | GitHub Actions + Fastlane |
| Tests | Jest, 211 tests across 41 `describe` blocks in one suite |
| Admin | Standalone static HTML/JS panel (`admin/index.html`) — **currently a client-side mock, not wired to the real backend**, see [Known Issues](KNOWN_ISSUES.md) |

## App bootstrap flow (`App.tsx`)

`App.tsx` is a state machine, evaluated in this priority order on every render:

1. **Splash** — while auth is loading, onboarding-seen flag hasn't loaded, or a T&C check is in flight.
2. **Onboarding** — first-launch only, gated by an `AsyncStorage` flag (`onboarding_complete`), shown before login.
3. **Login** — shown when there's no authenticated user (`useAuth().user` is null).
4. **T&C consent gate** — checked on **every login** via `tcService.checkTCAcceptance()`. If the
   admin has published a newer T&C version than the user accepted, a non-dismissible
   `TCConsentModal` blocks the entire app (Android back button disabled, Decline exits the app).
   If the check itself fails (e.g. offline), the app fails open rather than blocking the user.
5. **Health profile setup** — shown once per user (AsyncStorage key keyed by user id), immediately
   after first login + T&C acceptance.
6. **Main app** — bottom tab navigator (`Home` → `Scan`/`Product` stack, `List`, `Profile`), with a
   persistent `OfflineBar` and a one-time `WalkthroughModal`.

## Core product flow

```
Barcode scan (ScanScreen)              Photo scan (PhotoScanScreen)
        │                                        │
        ▼                                        ▼
 foodApi.fetchProductByBarcode          photoScanService.analysePhotoMeal
   (Open Food Facts + accuracyEngine)     (Claude Vision)
        │                                        │
        ▼                                        │
 ProductScreen: parallel-loads                   ▼
   • priceApi.fetchPricesByBarcode        DiaryScreen entry (macros, meal type)
   • aiHealthService.analyseProductForUser
     (Claude + user healthProfile)
        │
        ├─ if verdict ≠ "safe" → recommendationService.findSimilarProducts (Claude-ranked alternatives)
        ├─ userDataService.saveScanHistory (AppSync → DynamoDB)
        └─ shoppingListService.addToShoppingList (local AsyncStorage list)
```

Health verdicts and warnings are produced two ways that feed each other:
- **Rule-based**: `userDataService.generateWarnings()` cross-references the user's structured
  health profile (allergies, conditions, diet type) against product allergens/ingredients.
- **AI-based**: `aiHealthService.analyseProductForUser()` sends the same profile + product data to
  Claude for a personalised natural-language verdict, falling back to a local rule-based heuristic
  if the API call fails, and to canned mock data if no API key is configured.

## Data ownership

- **Structured, durable data** (user record, health profile, scan history) lives in **DynamoDB**
  via AppSync GraphQL, owned per-user (enforced in AppSync JS resolvers via `ctx.identity.sub`,
  not schema `@auth` directives).
- **Local-only data** (food diary entries, shopping list, CMS page cache, T&C acceptance cache,
  logger/error ring buffers) lives in `AsyncStorage` on-device and is not synced to the backend.
